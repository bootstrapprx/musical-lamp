# Musical Lamp Domain Contract

**Status:** Phase A consolidated contract
**Schema namespace:** `musical-lamp/v1`
**Execution boundary:** standalone local Rust daemon; local Docker executor only

## 1. Scope

Musical Lamp is a generic deployment control plane for composing and operating Frappe-based products. Accounting and Trivia are reference blueprints. They are not Rust product types and must not require product-specific branches in the engine.

The control plane is authoritative for registry validation, dependency resolution, compatibility decisions, plan generation, execution, reconciliation, persistence, and operation history. The TUI and future React/TypeScript/Vite frontend are clients.

The daemon binds to loopback by default, authenticates clients, redacts sensitive values, and never exposes a public API implicitly. Remote execution is unsupported in v1.

## 2. Core entities

### 2.1 App registry entry

An app is an independently registered component. It has a stable ID, source provenance, an immutable production reference, compatibility constraints, dependencies, installation metadata, and validation evidence.

Frappe is a **framework requirement** and the base of a bench. It is not a site-installable application. ERPNext, LMS, trivia_sync, and future components are installable applications.

Each registry entry classifies configuration fields as:

- `public`: safe to show and persist normally;
- `sensitive`: credentials or secret material; persisted only by secret reference;
- `derived`: generated by the planner/executor;
- `user_supplied`: supplied during onboarding and validated against the schema.

An endpoint or repository URL is not automatically sensitive. API credentials are sensitive.

### 2.2 Product blueprint

A blueprint is a versioned, reusable composition. It declares the selected installable applications exactly once. It declares the framework requirement separately. The resolver derives the transitive application set and installation order.

A blueprint contains no secret values. Sensitive settings use `secret_ref`; ordinary endpoints remain public configuration unless the app explicitly classifies them otherwise.

The site list is part of the blueprint. Multiple named sites are supported by the model, although the first complete executor may provision one site per deployment.

### 2.3 Deployment plan

A plan is a deterministic, reviewable result of resolving and validating a blueprint. It records exact immutable source refs, framework resolution, application closure, dependency order, compatibility checks, image policy, required secrets, preconditions, and ordered execution steps.

Confirmed incompatibility always blocks execution. Unknown compatibility blocks execution by default. A justified override may permit unknown compatibility only; it must not bypass confirmed incompatibility and must be recorded in the plan and audit history.

### 2.4 Deployment instance

An instance records an approved plan and what was actually deployed: blueprint revision, source commits, sites, installed apps, runtime resources, desired state, observed state, health, and operation history.

Desired state and observed state are separate. A successful command is not evidence that the desired state was reached; reconciliation is required.

### 2.5 Operation

Every asynchronous command has an operation ID, deployment ID, kind, lifecycle status, ordered events, timestamps, and failure details. Operations are persisted in SQLite and can be queried by either client.

## 3. Resolution rules

1. Validate the blueprint and selected registry IDs.
2. Resolve the required framework/base independently from installable apps.
3. Compute transitive application dependencies to a fixed point.
4. Reject missing apps and dependency cycles.
5. Validate framework and app compatibility.
6. Resolve every source ref to an immutable commit/digest.
7. Topologically sort installable applications deterministically.
8. Validate runtime, site, secret-reference, and host prerequisites.
9. Generate a deterministic plan hash from canonical input and resolved output.
10. Refuse execution when any blocking finding remains.

For Trivia, the registry records `trivia_sync -> lms`; the blueprint selects `trivia_sync` once and the resolver derives `lms` plus the Frappe framework requirement.

## 4. Image policy

The blueprint must explicitly select `build` or `pull`. The executor must not silently change policy during a deployment. A build plan records build inputs and provenance; a pull plan records the immutable image reference. Runtime images and infrastructure images must be immutable for production execution.

## 5. Persistence

SQLite is authoritative for operational state, deployment instances, operations, events, migrations, and audit history. YAML is the import/export and version-control format for registries and blueprints. Schema versions and database migrations are required from the first persistence implementation.

Secret values are never stored in blueprint YAML, plan responses, normal operation events, or diagnostic output.

## 6. API boundary

The future local API exposes registry, blueprint, plan, deployment, reconciliation, and operation resources. Clients do not invoke Docker, Compose, or Bench directly. Event streaming may use SSE or WebSockets; the domain contract is transport-independent.

## 7. Reference blueprints

The examples in `blueprints/examples/` are intentionally incomplete where production compatibility has not yet been established. They are contract fixtures, not authorization to promote mutable branches or guessed refs to production.

- Accounting selects `erpnext`; Frappe is resolved as the framework.
- Trivia selects `trivia_sync`; the registry derives `lms` because `trivia_sync` requires it, and Frappe is resolved as the framework.
- The unresolved accounting custom app is not invented.

## 8. Test strategy

### Schema tests

- Validate every checked-in registry and blueprint fixture.
- Reject duplicate selected app IDs, embedded secret values, missing framework requirements, invalid IDs, and unsupported schema versions.
- Validate configuration classification and secret-reference shape.

### Resolver tests

- Resolve framework versus installable apps correctly.
- Compute transitive dependencies.
- Produce stable topological order.
- Detect missing dependencies and cycles.
- Reject confirmed incompatibility.
- Block unknown compatibility unless an auditable override is present.
- Resolve mutable refs only into an explicit non-production investigation result; production plans require immutable refs.

### Planner tests

- Generate byte-for-byte deterministic plans from identical inputs.
- Include exact source commits, dependency closure, installation order, image policy, preconditions, and expected outcomes.
- Ensure the selected application composition appears only once in the blueprint and is expanded only in the plan.

### Persistence tests

- Apply SQLite migrations from an empty database.
- Persist and reload blueprints, plans, instances, operations, and ordered events.
- Preserve operation history across restart.
- Reject invalid schema versions.
- Verify secret values never appear in persisted blueprint/plan/event payloads.

### Executor/reconciliation tests

- Use a fake executor for deterministic command sequencing and failure injection.
- Verify idempotent readiness, site creation, app installation ordering, and migration steps.
- Verify partial failure is represented explicitly.
- Verify desired state is not rewritten as observed state before reconciliation.
- Verify reconciliation derives service/site/app state from observations rather than last requested action.

### Reference workflow tests

Run the same generic path for Accounting, Trivia, and a third temporary composition. The test must prove that no product-specific engine branch is needed.

End-to-end Docker tests must use isolated project names, volumes, networks, and disposable sites. They must never target an existing production deployment.
